## Findings

| ID | Severity | What is wrong | Proof | Suggested fix |
|---|---|---|---|---|
| F1 | **blocker** | Any keyword or exclude-keyword containing a literal hyphen (`work-from-home`, `T-Mobile`, `COVID-19`, `self-hosted`, `n8n-nodes`...) crashes the **"Find new posts that match your keywords"** Code node with an uncaught `SyntaxError`, because `escapeRegex` backslash-escapes `-` (`\-`), which is an **invalid escape under the regex `/u` flag outside a character class**. The node has no `onError`/try-catch, so the whole scheduled run fails for *every* configured channel, every time, until the keyword is removed. This directly violates AC7 ("Regex special characters in keywords ... are treated literally") and none of the 77 tests, including the two property tests, ever construct a keyword containing a hyphen. | `node scratch/probe6.mjs` → `FAIL "a-b" -> Invalid regular expression: /(?<![\p{L}\p{N}_])a\-b(?![\p{L}\p{N}_])/iu: Invalid escape` (every other escaped metacharacter — `. * + ? ^ $ { } ( ) \| [ ] \ /` — is fine, only `-` fails). `node scratch/probe9.mjs` → with channels `jobs`/`news` and keywords `['work-from-home','kubernetes']`, both channels' alerts are lost: `ENTIRE RUN CRASHED ... SyntaxError: Invalid regular expression: /(?<![\p{L}\p{N}_])work\-from\-home(?![\p{L}\p{N}_])/iu: Invalid escape` | In `src/find-new-posts.js` `escapeRegex`, stop escaping `-` (it has no special meaning outside a character class, so it never needs a backslash): drop it from the character class, e.g. `s.replace(/[.*+?^${}()|[\]\\\/]/g, '\\$&')`. Add a regression test with a hyphenated keyword, and extend the AC7 property test's keyword alphabet to include `-` and the other escaped metacharacters, not just `a-z`. |
| F2 | minor | `cutSnippet()` (post snippet, 500 chars) and `clip()` (used for the `Matched: ...` keyword list, header and link, AC15's own overflow guard) truncate by UTF-16 **code unit**, not code point. When the cut lands exactly inside an astral emoji's surrogate pair and there is no whitespace nearby for `cutSnippet`'s word-boundary rescue to find, the text actually sent to Telegram contains a lone/unpaired surrogate right before the `…`. | `node scratch/probe3.mjs` → with 498 non-space chars + 😀 + 50 more non-space chars, `lone surrogate in snippet? { index: 498, type: 'high-no-low' }` and the same lone surrogate (`\ud83d`) appears in the full alert `text` that would be POSTed to the Bot API. `node scratch/probe7b.mjs` → direct proof against the shipped `clip()` function: `clip('a'.repeat(299) + '🚀' + 'b'.repeat(20), 300)` → tail `"aaa\ud83d…"`, lone surrogate confirmed. | Before slicing at the limit, back off one more character if the code unit at the cut index is a high surrogate (`0xD800`–`0xDBFF`), in both `cutSnippet` and `clip`. |
| F3 | minor | Dedupe state read from workflow static data is used as `lastSeen + 1` for the gap check. If `lastSeen` is ever a **string** (e.g. a user hand-edits the static-data JSON in the n8n UI, or it survives from an older version of this or another workflow sharing the same static-data namespace), `"5" + 1` is **string concatenation** (`"51"`), not numeric addition, so `lowest > lastSeen + 1` compares against the wrong, much larger bound and silently fails to flag a real gap. (The code itself always *writes* a number via `Math.max`, so this needs external interference to trigger — hence minor, not blocker.) | `node scratch/probe2.mjs` → with `lastSeen_alpha: '5'` (string) and a new lowest post id of 10 (a real gap: posts 6,7,8,9 missing), `possibleGap = false` — should be `true`. | Coerce with `Number(lastSeen)` once right after reading it from static data (also hardens against the array/null shapes noted below, which already behave safely today: `node scratch/probe1.mjs` shows `null` and `[5]` do not crash and do not hide a gap). |
| F4 | minor | The HTTP Request node's `maxTries: 2` and the Telegram node's `maxTries: 3` were set to literally match SPEC's "retry on fail 2 times" / "retry on fail 3 times" wording, but n8n's `maxTries` field is the **total number of attempts** (clamped to a minimum of 2), not the retry count. So the HTTP node actually retries only **once** (not twice) and the Telegram node only **twice** (not three times). | Read `/workspace/n8n-local/node_modules/n8n-core/dist/execution-engine/workflow-execute.js`, `getRetryParams()`: `[Math.min(5, Math.max(2, node.maxTries \|\| 3)), ...]`, and the loop in `get-input-connection-data.js` runs `tryIndex < maxTries` times total. With shipped `maxTries: 2`/`3`, total attempts are 2/3, i.e. 1/2 retries. | If the intent is N retries beyond the first try, set `maxTries` to 3 (HTTP) and 4 (Telegram), or note the "total tries" interpretation in NOTES.md and leave as-is — either way, document the discrepancy. |

No other adversarial input from the review brief (cross-host `href`, duplicate post ids across blocks, uppercase/dotted/@-prefixed/full-URL channel names, Polish whole-word diacritics, media-only posts, ids going backwards, `baselineOnFirstRun: false`, `maxAlertsPerRun: 1` with 3 matches, non-numeric ids, transport-error-plus-good-channel, empty keyword lists, leading/trailing keyword whitespace, exclude keywords) turned up a defect; see probes `probe1.mjs`, `probe4.mjs`, `probe5.mjs`, `probe8.mjs` for the checks that came back clean, each printing `OK`/expected values.

## Spec gaps and weak tests

- **Property tests never fuzz keyword content with regex-special characters.** `tests/property.test.mjs`'s AC11 test randomises *post text* over an alphabet that happens to include `$`, `.`, `+`, `<`, `>`, `&`, `"`, `'` — but always as literal post text with a fixed, hyphen-free sentinel keyword (`propertymatch`). The AC7 property test randomises *keywords* but only from `a-z` letters. Neither can ever hit F1; a property test that also fuzzes keyword/exclude-keyword content over the escaped-metacharacter alphabet (including `-`) would have caught it.
- **No fixture exercises a forwarded post.** `fixtures/durov.html` has exactly one `.tgme_widget_message` per `.tgme_widget_message_wrap` (20 wraps, 20 `data-post` attributes, confirmed by grep). Real public channels frequently forward posts, which embed a *second*, nested `.tgme_widget_message` (the original, forwarded-from post) inside the wrap. The "Extract fields from each post" HTML node's `postId`/`text`/`isoDate`/`url` selectors (`.tgme_widget_message`, `.tgme_widget_message_text`, etc.) are not scoped to avoid a nested match, so which element wins (outer forwarding wrapper vs. inner forwarded message) is untested and not verified against real n8n Extract HTML Content behaviour for multiple matches. This can't be proven offline without a new captured fixture; recommend capturing one real forwarded post and adding it to `fixtures/`.
- **AC14 live-run claims are unverifiable in this review.** `VERIFICATION.md` reports "12 of 12 checks pass" and `README.md` repeats the number; I did not run `npm run e2e` (per review scope) so I could not independently confirm this. I did check the hand-edited correlation logic in `scripts/e2e.mjs` (commits `7db78ec`/`09cbf10`) against the real installed Telegram node source (`Telegram.node.js`): for `resource: 'message', operation: 'sendMessage'` the node's output `json` is the **full** Bot API response body (`{ ok, result: { message_id, ... } }`), not unwrapped — so `j?.message_id ?? j?.result?.message_id` in `runPhase()`'s id-correlation correctly falls through to `j.result.message_id`. That part of the hand edit is correct.
- **Node count (11) is just under SPEC's "target 12 to 16"** — disclosed honestly in `NOTES.md` ("I kept to the described flow rather than padding with a node that does nothing"); not a defect, SPEC calls it a target not a hard minimum.
- Docs (`README.md`, `LISTING.md`, `NOTES.md`, `docs/sticky-colours.md`), sticky note text, test count (77, matches `npm test` output) and the copy lint all check out; no secrets, personal emails, chat ids or the author's name appear in `workflow.json` or any shipped doc.

## Verdict

**FAIL** — F1 is a blocker: a single, very ordinary hyphenated keyword (the kind of term the
target audience for a jobs/deals/tenders alert template would plausibly type) permanently breaks
every scheduled run until edited, and it is completely uncovered by the existing 77 tests.
