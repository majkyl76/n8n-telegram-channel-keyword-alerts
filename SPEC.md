# SPEC: Send Telegram alerts for keyword matches in public Telegram channels (no Telegram API key for reading)

Status: ready to build. Audience: people who follow public Telegram channels (news, jobs, deals, releases, tenders) and want a ping only when something relevant is posted.

## Background
Telegram publishes the last ~20 posts of any public channel as plain HTML at `https://t.me/s/<channel>`. No login, API id or user session is needed. Existing n8n templates for "Telegram channel" either post TO channels or rely on a paid Apify actor (ids 17733, 17734). None reads the public web preview directly, dedupes, filters by keywords and alerts. This fills that gap with only core nodes.

## Problem
Following many channels means scrolling through noise. People want: "tell me when any of these 5 channels mentions *kubernetes*, *n8n* or *remote*, once per post, with a link".

## Scope
A scheduled workflow that, for each configured channel: fetches `t.me/s/<channel>`, parses posts, finds posts newer than the last one seen, keeps those matching the keywords, and sends one Telegram message per match (capped per run) through a Telegram bot to a chat the user chooses.

## Out of scope
Fetching older history (`?before=`), media download, translation, AI, private channels/groups, reading channels the user is not able to open in a browser without login, Slack/email delivery (mention how to swap the last node in the Customization note only).

## Nodes and flow (target 12 to 16 nodes plus stickies; use core nodes only)
1. `Run every 15 minutes` (Schedule Trigger, default every 15 minutes) and `Run manually` (Manual Trigger) both feed the config.
2. `Set up your channels and keywords` (Set node, the ONLY place a user edits values): `channels` (multi-line string, one per line, accepts `name`, `@name`, `t.me/name`, `https://t.me/name`, `https://t.me/s/name`), `keywords` (multi-line, one per line, phrases allowed), `excludeKeywords` (optional, multi-line), `matchWholeWords` (boolean, default true), `telegramChatId` (default placeholder `YOUR_TELEGRAM_CHAT_ID`), `maxAlertsPerRun` (number, default 10), `baselineOnFirstRun` (boolean, default true), `previewBaseUrl` (default `https://t.me/s/`; exists so tests can point at a local mock and so people can use a mirror).
3. `Check settings and list channels` (Code): validates config and emits one item per channel (see AC4/AC9). Throws a clear error `NodeOperationError`-style message (plain `throw new Error(...)` is acceptable in a Code node) for: placeholder chat ID still present, no keywords, invalid channel name, no channels.
4. `Fetch channel preview page` (HTTP Request GET, one request per channel, batch size 1 with 1 s interval, 20 s timeout, never error on non-2xx and return full response so the status code is visible, sends a normal browser User-Agent header, retry on fail 2 times).
5. HTML parsing with the HTML node (Extract HTML Content): first node splits the page into post blocks (`.tgme_widget_message_wrap`, returning HTML), then Split Out, then a second HTML node extracts per post: post id from the `data-post` attribute (`channel/123`), message HTML (`.tgme_widget_message_text`), ISO datetime (`time` element `datetime` attribute), permalink (`a.tgme_widget_message_date` href), views. Posts without text (media only) must not break the alignment of fields.
6. `Find new posts that match your keywords` (Code, run once for all items): per channel, converts message HTML to plain text (`<br>` to newline, strips tags, decodes entities), compares post numbers with `lastSeenPostId` stored per channel in workflow static data, applies keyword/exclude matching, builds the alert items, applies the per-run cap, updates the static data, and builds channel-problem notices (see AC10) and the gap note (AC9).
7. `Anything to send?` (If) then `Send alert to Telegram` (Telegram node, Send Message, parse mode HTML, link preview off, retry on fail 3 times with 2 s wait). Credential `telegramApi` named exactly `Telegram Bot account` (name only, see AC3).
8. Section stickies (white) and one main yellow sticky, per AC2.

## Acceptance criteria
Each criterion needs at least one test whose name starts with the AC id. "Shipped" means the content of `workflow.json`.

- **AC1 Importable structure.** `workflow.json` is valid JSON with `name`, `nodes`, `connections`, `settings`. Node names unique, node ids unique, every connection source and target exists, every non-sticky, non-trigger node is reachable from a trigger, no disabled nodes, no orphan nodes. Every node `type` and `typeVersion` exists in the installed n8n-nodes-base (the test reads `/workspace/n8n-local/node_modules/n8n-nodes-base` if present and skips with a clear message if not). Workflow `name` is a verb-first plain title, at most 80 characters, no emoji. `active` is false. No `pinData`. No `id`, `versionId`, `meta.instanceId`, or other instance-specific fields.
- **AC2 n8n sticky note guidelines** (from n8n's "Sticky note guidelines for templates"): exactly one main overview sticky; yellow; top-left (its x and y are the minimum x and minimum y of all nodes and stickies, so nothing sits above or left of it); 100 to 300 words; contains the headings `### How it works` and `### Setup` (and optionally `### Customization`); the Setup section names every credential to connect, every value to edit in the config node, and how to test it, and states the static-data limitation. Because the workflow has 4+ nodes it needs white section stickies, each under 50 words, each with a short heading, each geometrically covering at least two nodes (and not covering the main sticky), covering all functional nodes between them. Red warning stickies are allowed only if each covers exactly one node; use at most one (put it on the Telegram node: set the chat ID and credential first). No other stickies.
- **AC3 No secrets, credentials by name.** No string anywhere in the JSON matches Telegram bot token pattern `\d{6,12}:[A-Za-z0-9_-]{30,}`, `Bearer `, `api_key`, long random strings, personal email addresses, personal chat IDs, or Michal's name. The Telegram node references credential type `telegramApi` with `name: "Telegram Bot account"` and no real id (omit `id` or set it so that n8n import accepts it; record in NOTES.md what you chose and why). No credential is used anywhere else. The HTTP Request node needs no credential.
- **AC4 Config validation.** The Code node in step 3 throws, before any HTTP request, with a human-readable message that names the problem, for: chat ID still `YOUR_TELEGRAM_CHAT_ID` or empty; no keywords; no channels; a channel string that is not a valid Telegram username after normalisation (5 to 32 characters, letters, digits, underscore, must start with a letter) with the offending value in the message; `maxAlertsPerRun` not a positive integer. Normalisation accepts every channel format listed in step 2, strips trailing slashes, query strings, `/123` post suffixes, de-duplicates case-insensitively, and ignores blank lines and lines starting with `#`.
- **AC5 Node naming.** No node uses an n8n default name (`HTTP Request`, `Set`, `Edit Fields`, `Code`, `If`, `Telegram`, `Schedule Trigger`, `Manual Trigger`, `HTML`, `Split Out`, with or without trailing numbers). Names describe the action, at most 50 characters.
- **AC6 Parsing.** With `fixtures/durov.html` through the shipped HTML nodes' selectors (the e2e run proves the real nodes; the unit tests prove the Code logic given the item shape the HTML nodes emit; write a small fixture-derived item set under `fixtures/` produced by Cheerio from `/workspace/n8n-local/node_modules` if available, otherwise by a documented hand-extraction, and say which in NOTES.md) the Code logic produces one candidate per post block (the fixture has 20 `data-post` attributes), each with `channel`, numeric `postId`, `url`, `isoDate`, `text`, `views`. Plain text conversion: `<br>` becomes a newline, tags stripped, entities decoded (`&amp; &lt; &gt; &quot; &#39; &nbsp;` and numeric), emoji images (`<i class="emoji">`) replaced by their alt/inner text, whitespace collapsed, no leftover `<` or `>` from tags.
- **AC7 Keyword matching.** Case-insensitive and Unicode-aware (Polish `żółć` matches `ŻÓŁĆ`). With `matchWholeWords` true, `ai` matches `AI tools` and `(AI)` but not `mail` or `Kuwait`; with it false, substring matching. Multi-word phrases match across any whitespace run. Regex special characters in keywords (`c++`, `.net`, `$BTC`) are treated literally. Exclude keywords veto a post. Result lists which keywords matched (original spelling from config, de-duplicated, in config order).
- **AC8 Deduplication and state.** State is stored in `$getWorkflowStaticData('global')` per channel as `lastSeenPostId`. Posts with id at or below it never alert. After a run, `lastSeenPostId` is the highest post id seen on the page, even when no post matched. Running the Code twice on the same page yields alerts the first time and none the second. With `baselineOnFirstRun` true, a channel with no stored state records the highest id and sends no alerts, but the run output says so. With it false, first-run posts alert subject to the cap. Channels are independent. Two channels with the same post numbers never collide.
- **AC9 Gap and cap handling.** If, on a non-first run, the lowest post id on the page is more than `lastSeenPostId + 1`, the run output for that channel carries `possibleGap: true` and the alert message for that channel includes a one-line note that some posts may have been missed because the preview shows only the latest posts (say the real reason: raise the run frequency). If matches exceed `maxAlertsPerRun`, only the NEWEST `maxAlertsPerRun` matches are sent as individual messages in chronological order, followed by one summary message `+N more matching posts not shown`. State still advances so they are not resent.
- **AC10 Channel problems.** An HTTP status other than 200, a request error, or a page with zero post blocks (for example a channel without a public preview or a misspelt name: `fixtures/none.html`) produces ONE notice message for that channel ("Channel @name returned no posts. Check the name and that the channel has a public web preview.") and then no further notices until the channel recovers (flag in static data). A recovery posts no message. One bad channel never stops the others.
- **AC11 Message format.** Telegram HTML parse mode. All dynamic text HTML-escaped (`& < >`). Message shape: bold channel title line with `@channel`, the date as UTC, formatted `YYYY-MM-DD HH:mm UTC`; a snippet of at most 500 characters cut at a word boundary with `…`; `Matched: kw1, kw2`; a link `<a href="...">Open post</a>` with the post permalink. Total length always under 4096 characters, even for hostile input (property test).
- **AC12 Honest limits are documented.** Sticky, README and LISTING all state: preview shows roughly the latest 20 posts; manual runs do not persist dedupe state (so a manual test alerts again each time); runs only from an active workflow; Telegram can change the preview HTML; only public channels with a web preview work; it is polite scraping (1 request per channel per run with a 1 s gap, default 15 minutes).
- **AC13 Copy quality.** README.md and LISTING.md and all sticky text pass `npm run lint:copy` (no em dashes, no banned words, British spelling check for a short list: organise/organize, colour/color, licence/license (noun), behaviour/behavior, summarise/summarize, analyse/analyze, centre/center, favour/favor; flag the American forms except where they are a literal API field or code identifier).
- **AC14 Live end-to-end (PM-run).** `npm run e2e` (you write `scripts/e2e.mjs`; it needs env `N8N_URL`, `N8N_API_KEY`, and starts local mock servers) imports `workflow.json` into the local n8n through the public REST API, creates a Telegram credential whose base URL points at a local mock Bot API, patches ONLY the config node values and the trigger interval in the imported copy, activates it, and asserts the real execution data. It covers: baseline run (no alerts), a second run with new matching mock posts (alerts arrive at the mock Bot API with correct text), a third run with no changes (zero alerts), a broken channel (one notice, then none), cap and gap behaviour. Write it after the unit tests pass; if the env vars are absent it exits with a clear message. Do not run it yourself unless `N8N_URL` is set.

- **AC15 Message length is bounded for every part (review F2).** The alert text is under 4096 characters even with a very long link or a very long list of matched keywords. If the snippet shrink is not enough, the matched list is cut with an ellipsis, then the link line is kept last and never cut mid-tag. Test with a 5000 character url and 300 matched keywords.
- **AC16 Post link comes from the channel and post id.** The link is `https://t.me/<channel>/<id>` built in the Code node from the validated channel name and numeric id, not copied from the page's `href`. A test with a hostile `href` proves the link is unaffected.
- **AC17 No test hook in the shipped JSON.** `$testExpose` and any other test-only code is absent from every Code node in `workflow.json`. The tests exercise the shipped code through its normal input and output only (a small test-only build or a vm harness that does not need a hook is fine).
- **AC18 Sandbox globals.** Done: static test bans `URL`, `Buffer` and similar in Code nodes (found live in the sibling template).
- **AC19 Error items never stop a run.** Every node between the HTTP request and the Code node that can receive an error or empty item (both HTML nodes, Split Out) has `onError` set to continue, and the Code node treats an item with no `data` or no post as a channel with no posts. Proven live by the dropped-connection phase of `npm run e2e` (a channel whose connection is reset).
- **Decision (review, spec gap): the gap note is attached only to alerts.** A gap in a run with no matching posts is silent. State this in the README limits.
